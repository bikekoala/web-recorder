# Glossary

Domain terms used across this codebase. Update when introducing new vocabulary.

## Action log

A timestamped sequence of high-level actions taken during a recording session. Each entry captures **what** happened (`type`), **when** (`t` ms since session start), **what was targeted** (selector / bbox / description), and **page state** (`scrollY`, `viewport`).

The action log is the bridge from "browser execution" to "cursor trajectory synthesis": the synth layer never reads the DOM or the video — it operates purely on the action log.

## Trajectory / synthesized cursor path

A 60fps sequence of `(t, x, y, cursorType, eventTags)` samples representing a fictitious human-like cursor that connects the targets in the action log. Generated by `ICursorSynthesizer`.

## Performance

The output of reconnaissance (`IReconnoiterer.recon()`): a complete, **pre-resolved**, **paced** action sequence the `PerformanceDirector` plays back deterministically on-camera. Each `PerformanceStep` carries its kind (click/scroll/type/dwell/...), a `ResolvedTarget` (selector + bbox + description) for steps that need one, per-step pacing (durations, `dwellAfter`), and an optional `expectAfter` (URL / visible-text assertion checked after the step). Schema-first — see `src/domain/performance.ts`. Distinct from the action log: the Performance is **intent**, the log is **what actually happened**. Replaced the old streaming-era `DirectorBriefing` in ADR §0034.

## PerformanceStep

One entry in a `Performance` — a single primitive action plus its resolved target (if any), its pacing, and its optional `expectAfter`. The Director executes steps in order; a step whose `expectAfter` doesn't match reality triggers a re-plan checkpoint.

## ResolvedTarget

An element the reconnoiterer has already located: `{ selector, bbox, description }`. Carried by the `PerformanceStep`s that act on an element (click, type, ...) so the Director never has to do its own element search on-camera.

## Reconnaissance / re-plan checkpoint

**Reconnaissance** = the off-camera phase where the reconnoiterer snapshots the page, picks every target, paces every step, and emits a `Performance`. All LLM reasoning for a recording happens here, before the recording window opens. **Re-plan checkpoint** = the single recovery hook during playback: when a step's `expectAfter` doesn't match reality, the `PerformanceDirector` calls the reconnoiterer again (now used as a re-planner) to rebuild the remaining steps from the diverged point. Capped by `config.maxReplans`; after that the Director plays out remaining steps as-is. Each fires a `replan` action-log entry. See ADR §0034.

## Aria-ref snapshot / recon draft

The **aria-ref snapshot** = `IPageSession.ariaSnapshot()` — a deterministic, ref-tagged accessibility tree of the page (Playwright's `page.ariaSnapshot({ mode: 'ai', depth })`: a YAML-ish outline where every actionable node carries a stable id like `[ref=e7]`, `<iframe>` contents inlined). It's the recon planner's view of the page (ADR §0036 — it replaced the `observeAll()` LLM enumeration). Refs are valid only in the page state at snapshot time; `IPageSession.resolveAriaRef(ref)` resolves one to a *durable* `{selector, bbox, description}` (`page.locator('aria-ref='+ref)` + a derived CSS/XPath that survives a page reset) — deterministic, no LLM, no fuzzy re-match.

A **recon draft** (`ReconDraftSchema`, `src/domain/recon-draft.ts`) = what the recon LLM emits before resolution: same shape as a `Performance` except `click`/`type` steps carry a `ref` (an id from the aria-ref snapshot) instead of a resolved `target`. `LlmReconnoiterer.recon()` parses it (Hard Rule 2), resolves each `ref` via `resolveAriaRef`, and assembles the `Performance`. A `ReconvergeDraft` is the bare `{ steps }` a reconverge call returns.

## Rehearsal walk / rehearsing reconnoiterer

The **rehearsal walk** is an extra off-camera step inside `IReconnoiterer.recon()` (ADR §0034 / Task #21 / §0036, component `RehearsalWalker` in `src/adapters/recon/rehearsal.ts`): after the LLM produces a draft and its `ref`s are resolved, the walker *executes the draft against the live page* — instantly (scrolls jump with `durationMs: 1`, dwells skipped; the plan's animation params are kept for the on-camera render), observing the real post-action state, and **rewriting each acting step's `expectAfter` to what was observed** (the "prophet" core: the on-camera assertion is *measured*, not guessed). When a step **diverges** (threw / `about:blank` / a click that changed nothing / an unmet `expectAfter` with no visible change), the walker first tries the dead-click *recovery* sweep (the other `resolveTargetCandidates` for the accessible name), then a `reconverge` callback (capped, deadline-bounded — given a *fresh* aria-ref snapshot) for the rest of the plan; on cap/deadline it truncates + appends a graceful tail. Then it re-navigates to the start URL so the on-camera run reproduces the start state. (It does **not** re-resolve click/type targets per step anymore — §0036's aria-ref resolve is reliable, and the click executor selector-falls-back if the bbox went stale.) Output canary: `Performance.rehearsal = {walkedSteps, divergences, reconverges, truncated, timedOut}` (surfaced in `RunMetrics`). A **rehearsing reconnoiterer** is `LlmReconnoiterer` with this walk enabled (`config.reconRehearse`, default on). `RECON_REHEARSE=false` skips it (faster dev iteration).

## Viewport-relative coordinates

`(x, y)` measured from the top-left of the visible viewport at a given moment. Distinct from page-absolute coordinates which would shift when the page scrolls. The action log records viewport-relative coords plus `scrollY` so synth can render the cursor on top of the recorded video correctly.

## Port / Adapter

**Port** = an interface in `src/ports/` defining a capability the core needs (`IPageSession`, `IReconnoiterer`, `IDirector`, `IRecordingJudge`).
**Adapter** = a concrete implementation in `src/adapters/` (`StagehandPageSession`, `LlmReconnoiterer`, `PerformanceDirector`, `LlmVisionJudge`).

A new tech choice should always become an adapter, never a `core/` import.

## Session

One end-to-end recording attempt: `start() → goto → act/observe/scroll/wait* → stop()`. Owns one Browser + BrowserContext + Page + recordVideo file. Always cleaned up in `finally`.

## Blocker dismisser

`IBlockerDismisser` (port) / `LlmBlockerDismisser` (adapter, its own `gpt-4o-mini` client) — the off-camera step (ADR §0035 / Task #20) that clears **dismissable overlays** (cookie/consent banners, X-to-close newsletter/app-install modals) from a page before the `Performance` is planned and before recording opens. Owned by `LlmReconnoiterer`; runs a probe → detect → click → re-probe loop: probe `pageDiagnostic().blockerSignals` (empty ⇒ no LLM call, return), else a few rounds of "screenshot + observed elements → vision LLM picks the dismiss control → click it → re-probe", capped (3 rounds / 10 s). Best-effort — never throws; `stillBlocked: true` on a cap/error. Called at the top of `recon()` (so the plan sees a clean page) and on the rehearsal walk's page-reset (the walk reloaded the page; re-clean it for the on-camera run). Outcome on `Performance.blockerDismissal = {rounds, dismissed[], stillBlocked}` → `RunMetrics.blockerDismissal`. Does **not** touch region/age gates or paywalls. Gated by `config.blockerDismiss` (default on). The §0034-era stopgap — "the recon prompt plans an accept-cookies click as the first `Performance` step" — stays as a backstop for overlays that appear mid-recording.

(Was `BlockerPrelude`, a streaming-era pre-recording phase coupled to the removed `IFastDecider`, deleted in §0034 Task 8 — reborn here without that coupling.)

## Page diagnostic

A coarse page-health snapshot (`url`, `title`, `interactiveElementCount`, `visibleHeadings`, `blockerSignals`) returned by `IPageSession.pageDiagnostic()`. Same shape as the body of the `page_diagnostic` ActionLogEntry variant, minus `t`/`scrollY`/`viewport` which are filled in by the caller when (and if) the snapshot is logged. Heuristic-only — false positives/negatives are expected.

## Architecture A / B / C

Three competing recording approaches considered in [`decisions.md`](./decisions.md) §0001:

- **A**: xvfb + xdotool driving real OS cursor.
- **B** (current choice): pure headless + post-process cursor overlay.
- **C**: in-page injected fake cursor `<div>`.
